# T03 — Hook semantics from source

Question: When do candidate hooks fire, what do they contain, and can provenance be tagged?

Why it matters for the sync layer: Observation coverage, ordering, echo suppression, and dirty/undo state depend on semantics rather than declarations.

Method: Source query `query T03 VERSION Engine/Source 'OnObjectTransacted.Broadcast|OnObjectPropertyChanged.Broadcast|OnObjectModified.Broadcast|PackageDirtyStateChangedEvent.Broadcast|PackageMarkedDirtyEvent.Broadcast|OnDataTableChangedDelegate.Broadcast|struct FTransactionContext|class FTransactionObjectEvent|enum class ETransactionObjectEventType|enum class ETransactionStateEventType'`; read declaration and call sites; `compare T03` hashes and diffs. All inspected broadcasts are synchronous on the caller's thread: no dispatch/marshalling in these functions. This is NOT evidence all hooks always run on game thread. 5.8 TS DataTable delegate makes its delegate access thread-safe, not arbitrary UObject/table access safe. The scoped DataTable change itself uses a critical section. Expected editor/RC paths are game-thread paths; runtime thread and frequency must be measured in T08. Direct pointer writes without Modify/PostEditChange/HandleDataTableChanged have no automatic interception here. Event-source coverage is not guaranteed for arbitrary scripts.

DataTable RowMap is an ordinary `TMap<FName,uint8*>`, not a reflected UPROPERTY (`Runtime/Engine/Classes/Engine/DataTable.h:98-111`). SaveStructData serializes row name/data through custom native serialization (`Private/DataTable.cpp:158-184`); loading uses change scope (`:134-155`). ChangedRowName in HandleDataTableChanged is only supplied to each native FTableRowBase callback, NOT to the public table delegate. Thus these public hooks cannot by themselves identify arbitrary row or field changes; cache/diff or domain-specific editor hooks are necessary. Details-equivalent property events on other UObjects may supply useful property names.

Tagging: Core/Public/Misc/ITransaction.h `:19-35,42-76` contains TransactionId, OperationId, Title, Context, PrimaryObject. Transaction IDs stay with a history entry; BeginOperation creates a new OperationId (`EditorTransaction.cpp:802-811`), including undo/redo. Full-context FScopedTransaction constructor accepts context string, description, primary object (`Editor/UnrealEd/Public/ScopedTransaction.h:14-28`). Proposal: assign mutation provenance by transaction ID at start, suppress own finalized confirmation echo, BUT publish undo/redo as new authority changes (same transaction ID, new operation). Object event does not carry context directly; join against transaction-buffer state or maintained ID map. Existing Apply has a common description rather than operation ID tag: T09 must measure attribution.

Cancellation caveat: UTransBuffer::Cancel `EditorTransaction.cpp:1404-1455` broadcasts canceled and discards history, but does not restore object bytes. This differs from Concert's cancellation comment assuming an undo event already restored state. UE Shed's known explicit backup rollback is necessary; do not rely on FScopedTransaction::Cancel for rollback. Package dirty undo is maintained by transaction package records/fences (`EditorTransaction.cpp:25-51,695-696,832-842`), not the stale Serialize comment in Package.cpp. Saving changes the dirty fence, so undo can stay dirty even when returning to an earlier clean baseline. Runtime confirmation remains T10.

Evidence: [Compared source hashes](evidence/T03-source-comparison.txt); raw searches `out/sync-research/T03-5.7-source.txt`, `T03-5.8-source.txt`, diffs `T03-*.diff`. ITransaction.h, TransactionObjectEvent.h, EditorUndoClient.h identical. DataTable delegate changes ordinary→thread-safe; table change implementation core paths identical.

Final source supplement: `Editor/UnrealEd/Private/ScopedTransaction.cpp:20–29` is byte-identical across both engines ([hashes](evidence/audit-source-comparison.txt)); capture is gated by CanTransact / !GIsTransacting. `Classes/Editor/TransBuffer.h:70–138` in **both** engines creates a new undo entry only when ActiveCount was zero. A nested scoped transaction joins the existing entry; it does not establish independent per-edit undo. Runtime Apply during an active interactive transaction remains **UNVERIFIED**, and must be fenced/deferred or explicitly defined by a future authority adapter.

Confidence: high for read source and lack of row payload; medium for source-derived ordering; runtime frequency/thread/coverage UNVERIFIED.

Surprises / risks found: Modified is pre-write and coalesced, cancellation does not roll back, package save changes undo dirty behavior, UndoRedo alone does not say which direction, raw script pointer writes can evade notifications.
