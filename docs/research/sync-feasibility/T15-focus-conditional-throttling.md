# T15 — Disable background throttling only while UE Shed is focused

Question: Can Unreal preserve its background power policy while remaining responsive when UE Shed has foreground focus?

Why it matters for the sync layer: T11 found normal minimized editors throttle even with the checkbox disabled. A permanent global setting change is unnecessary if an editor capability can supply a conditional exemption.

Method: Follow-up authorized after the original research completed. Read `Engine/Source/Editor/UnrealEd/Classes/Editor/EditorEngine.h:660–662` (5.7) / `:691–693` (5.8): public `FShouldDisableCPUThrottling` delegates. Read `Private/EditorEngine.cpp:5014–5032` / `:5305–5323`: any true delegate returns false from ShouldThrottleCPUUsage before ordinary foreground/minimized checks. Built throwaway probe with `python research/sync-probe/fixture.py build 5.7`, then `build 5.8`. In PowerShell set `$env:UE_SHED_RESEARCH_EDITOR_UNATTENDED = "0"`; launch one engine, run `python research/sync-probe/focus_policy.py VERSION`, then `fixture.py stop VERSION`; repeat 5.8. Runtime driver forces the in-memory checkbox true without SaveConfig and leaves it true throughout measurements. No asset Save. Probe source `research/sync-probe/UEShedSyncProbe/Source/UEShedSyncProbe/Private/UEShedSyncProbe.cpp:48–89,269–276,297–311`; driver contains exact requests and assertions.

Results:

**Yes: the engine override and conditional foreground-process lease work on both versions, including minimized Unreal. Actual Workbench focus integration was not built or tested.** The existing Windows foreground process (Search, PID 18488, recorded native HWND) was registered as a controlled stand-in for UE Shed. No focus was stolen or simulated with a forged Boolean. The native comparison uses real foreground HWND → owner PID; mismatch registers the live Python client's different PID. This proves the predicate and engine behavior, not actual Electron/Workbench focus transitions.

| Normal editor case; checkbox remains true            | 5.7 one-cell Apply p95 | 5.8 one-cell Apply p95 | Effective throttle |
| ---------------------------------------------------- | ---------------------- | ---------------------- | ------------------ |
| Visible, registered foreground owner + valid lease   | 34.85 ms               | 27.50 ms               | false              |
| Minimized, no lease                                  | 335.59 ms              | 335.43 ms              | true               |
| Minimized, registered foreground owner + valid lease | 34.94 ms               | 34.98 ms               | false              |
| Minimized, lease explicitly released                 | 335.50 ms              | 335.85 ms              | true               |

Each case has 40 no-op and 40 sequential one-cell small-table Apply samples; nearest-rank p50/p95/max and native state are in the linked JSON. No-op is the probe early-return function. Both runs verify unattended=false and Unreal app/native focus=false. Each matched case checks an active predicate before/after and every ten samples. Large tables, GPU load and other FPS caps were not retested.

Additional assertions pass independently on both engines: live but non-foreground registered process → no exemption; 0.75 s lease expires after 1.1 s without renewal → normal throttling; removing only our delegate → normal throttling. Native owner comparison is evaluated by Unreal's throttle decision, so switching to an unrelated process does not require waiting for an RPC blur message. An actual OS focus-switch sequence was not performed; this was controlled owner-match/mismatch testing. Registration uses a held process handle and liveness check, which guards identity while that handle is held. The research renewal path reopens a PID; a product capability should validate owner identity/session generation once and renew that identity rather than accept arbitrary/reused numeric PIDs.

Engine build outcomes: first 5.7 compile failed because guessed CloseProcHandle does not exist; corrected to verified `FPlatformProcess::CloseProc` (`Runtime/Core/Private/Windows/WindowsPlatformProcess.cpp:734–740` / `:742–748`). Final builds passed: 5.7 6.32 s; 5.8 9.60 s. Engine `OpenProcess` currently requests PROCESS_ALL_ACCESS (`:713–715` / `:721–723`); the tested foreground stand-in accepted it. Minimal process rights / denial handling require a product design. Native foreground helper mirrors the APIs used by ApplicationCore (`WindowsPlatformApplicationMisc.cpp:107` / `:195`). No engine implementation copied.

Suggested integration (proposal, not implemented): an editor capability registers its own conditional delegate and accepts a short-lived activity lease bound to an explicitly connected client. Workbench's main process derives activity from focus/blur events and `BrowserWindow.getFocusedWindow()`, renews while one of its relevant windows is focused, and releases on blur/disconnect. On Windows, also verify the registered host process owns the foreground window on each native decision. Browser-only hosts need page/window visibility and focus reporting; CLI hosts need their own policy. The native capability belongs in the public connection/engine layer; Workbench supplies focus intent as one client. Keep the existing checkbox untouched and resume normal Unreal policy when our predicate is false; other engine/plugin exemptions may still keep Unreal active.

Wake-up limit: first lease acquisition over RC while Unreal is already throttled waits for its current idle tick. The 5.7 acquisitions after throttle were about 333 ms (raw request timings). Subsequent Apply timings above are steady-state with the lease active. This override does not promise sub-100 ms initial activation or change unrelated frame-rate caps. A connected owner registration can avoid requiring an RPC on every focus transition, but wake scheduling still needs measurement.

Confidence: high for both engine builds, override/foreground predicate and measured loopback cases; medium for the integration design; low for untested actual Workbench/OS transition timing and other platforms.

Surprises / risks found: The override bypasses minimized throttling as well as the checkbox. Returning false restores normal policy rather than forcing throttle, so unrelated engine exemptions remain respected. First wake can still cost an idle tick. Public collection is an array of delegates, not a multicast event: retain your delegate handle and remove only that entry on shutdown, never clear other plugins' exemptions.

Open follow-ups: Implement a separately reviewed client activity capability and actual Workbench focus adapter; test multiple windows/projects, foreground switches, blur/crash, delayed/out-of-order renewals and process identity reuse; measure first focus wake and minimized CPU/GPU cost. Native Win32 focus probe is Windows-only; cross-platform focus-intent leases remain unverified.
